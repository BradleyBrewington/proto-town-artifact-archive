DSIP via Chrome only; navysbir.com and armysbir.army.mil via WebFetch; none via a clean API
  • The authoritative DoD source (DSIP, dodsbirsttr.mil) is unreachable from the cloud side. WebFetch refuses every path (robots.txt policy). The only working route today is your Chrome browser on solomon, which is slow, manual, and not something an agent fleet can run on.
  • Through Chrome I reverse-engineered the full DSIP public JSON API (section 6). It is unauthenticated, returns every field you care about (objective, Phase I/II/III text, keywords, ITAR, CMMC, tech areas, references, published Q&A, TPOC during pre-release, per-topic PDF, instruction PDFs). That is the primary build target. One Python collector against it gives you 100% of DoD.
  • TPOC names and emails are exposed only while a topic is in Pre-Release (showTpoc:true, topicManagers[]). Once it opens, showTpoc:false, topicManagers:null. Your collector must run during the pre-release window (first Wednesday of month, ~3 weeks) or you lose the TPOC data permanently.
  • SBIR.gov is the only cross-agency aggregator that works, but only its HTML (10 rows/page, no agency filter that works, detail pages lack objective/phases/TPOC/ITAR). Its JSON API returns {"message":"Forbidden"} server-side; it is down for maintenance, not blocked by my tooling.
  • Civilian agencies are a patchwork: NSF is fully readable (HTML); NASA and DOT are PDF-only; NIH grants are on simpler.grants.gov; NIH/NASA/ED/DHS/EPA contract solicitations live on SAM.gov (JS shell, needs your API key); DOE OSTI sub-pages return 403; DHS portal DNS fails. Nothing civilian is open for Phase I right now except NSF (11/4) and NIH (9/5), plus ARPA-H (9/11) and NCI (9/21).
  • Your existing local tools (sam_search.py, paul.duckdb, the local sbir-search MCP) are invisible from this session. No folder is connected, so device_bash cannot run them. Connect the Projects folder and they become usable here.
  • Net gap to "complete awareness": 5 tools, roughly 6 to 9 working days (section 8). Two of them (DSIP collector, SBIR.gov scraper) cover ~90% of the value.

8Build spec, in priority order

TOOL 1 DSIP collector (Python, runs on solomon, daily + on demand)

  • Inputs: none. Config: cycle filter (default openTopics + explicit archived cycles for backfill).
  • Steps: /topics/solicitations → /topics/search (size=100, page through) → per topic /details, /questions, /download/PDF, every referenceDocuments[].uploadId, every baaInstructions[].uploadId and the release preface. Strip HTML to text; keep raw HTML too. Convert epoch ms to ISO with ET offset.
  • Storage: one JSON per topic ({topicCode}.json) + PDFs in a folder + a DuckDB table (dsip_topics) outside PaulPipeline. Snapshot per run; diff runs to detect new pre-release topics, TPOC appearance, Q&A additions, removals, date changes.
  • Headers: browser UA, Accept: application/json, Referer: https://www.dodsbirsttr.mil/topics-app/. Retry 503 with backoff (observed). Throttle ~1 req/s.
  • Fallback if WAF blocks non-browser clients: Playwright Chromium on solomon executing the same fetch() calls in-page (proven to work today).
  • Expose as an MCP server (list_open_topics, get_topic, get_qa, diff_since) so Cowork agents query the local store instead of the web. Use the mcp-builder skill.
  • Effort: 1 to 2 days. Covers ARMY, NAVY, USAF/USSF, DARPA, OSD, DMEA, DTRA, DHA, MDA, SOCOM, DLA, NGA, CBD, DISA. This is ~90% of your target universe.

TOOL 2 SBIR.gov topics scraper (cross-agency cross-check)

  • Collectors write one normalized JSON per topic (schema: id, code, agency, component, program, phase, dates, status, itar, cmmc, text blocks, keywords, tech areas, tpoc, qa[], pdf_paths[], source_urls[]) to a local store + DuckDB. Agents never touch the web.

Stage 2: one agent per surviving topic scores Technical Fit / Feasibility / Strategic / Competition and emits the spreadsheet row. Stage 3: a completeness agent reconciles counts against SBIR.gov and BW&CO totals so a miss is detectable, not silent.
  • Volume is small: 60 DoD topics per month plus ~30 civilian items per quarter. Per-topic agents are affordable; the risk is stale data, not compute.

9Caveats on this audit

  • Every WebFetch result was a model summary; where an agent reported a field absent, the field may exist but was dropped by the summarizer. The DSIP field lists in section 6 are exempt: they came from raw JSON in your browser.
  • Topic counts: DSIP 60 (56 open + 4 pre-release, includes CSO/xTech entries and future-dated releases); BW&CO 51 for Release 5 proper; SBIR.gov 337 open across all agencies; Federal Atlas 305. I did not reconcile them one-to-one; Tool 2 will.
  • DSIP status codes 591/592 are inferred from the UI filter (Pre-Release, Open checked). Verify by toggling filters and re-reading the network log.
  • The topicId format (hash_number) suggests IDs are not stable across cycles; key your store on topicCode.
  • The cloud shell could technically reach these hosts; I did not use it because this session's policy forbids routing around WebFetch blocks. That restriction does not apply to scripts you run on solomon.
  • No aggregator or agency site has been checked for FY27 civilian releases that post after today; Tool 5 exists for that reason.
