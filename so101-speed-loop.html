Speed Loop

A reviewer agent tunes a 3-minute executor agent until the arm runs pick-and-place fast from anywhere in the workspace. Nothing is recorded while it runs. Then that executor records the next dataset.

Status. Harness built, dry-run tested, committed (tag good = baseline tools), service installed but not started. The robot is disconnected; the first real iteration is the baseline test. Start: systemctl --user start speedloop. Stop: touch state/HALT_SPEEDLOOP. Board: iters/board.md. Live timer: the camera page at port 8090 shows the current phase, the executor countdown from wake to kill, the done mark, the last result and the running tally.

What the factory does today, in the terms that matter here

The supervisor (factory.sh, systemd unit factory) spawns one claude -p sortie at a time with a budget of 8 episodes or 40 minutes. Inside the sortie the agent's nominal loop is four scripts: coverage.py next, reset_to.py, episode.py, coverage.py mark. The LLM is never inside the motion. Every streamed move ran at a fixed 30 degrees per second, and nothing in tools/ could change that. So the arm has run at one speed for all 93 episodes.

The speed loop walks the full 70-cell serpentine order, every cell including the 12 the factory marked hard, wrapping into a new pass. A block of 3 consecutive runs therefore probes one strip of the table; the reviewer prompt says so and tells it to read across blocks. Cells whose reset fails twice are skipped for the rest of the pass and get one more try next pass. How recording is locked out

The supervisor writes state/sortie.json with the episode counter already at the cap before every iteration. The frozen record gate refuses to open the dataset, so episode.py can only run with --rehearse; the executor's permissions and prompt say the same thing, but the lock is structural.

Score

Primary: success rate over the last 9 executor runs at or above 80 %. Second: median time to done of successful runs. Third: motion time, since that is what the policy will imitate. Success = metric landing within 1.0 cm, or the judge's majority-on-X. A killed run scores 180 s if the roll still ended on the X, and a failure otherwise.

Guardrails in the frozen layer

  • Speed ceilings. calib/motion.json is read by lib/arm.py and clamped: transit legs at most 90 °/s, the descent, grasp, set and release phases at most 45 °/s. Baseline is 30/30, identical to every recorded episode so far.
  • Auto-revert. If a block scores 0/3 after the tool state changed and the previous block scored 2 or better, the supervisor restores the lever files from tag good and commits. A block at 2/3 or better moves good forward. Change detection hashes the lever files' content, not git HEAD, so review notes never look like a tool change.
  • Process-group kill. Executor and reviewer run under setsid; the deadline or cap kills the whole group, then a pkill sweep for any arm tool, then park. The reviewer's checkpoint photos move into its own rNNNN.runs/ folder so they never contaminate the next iteration's bundle.
  • Recovery. Two consecutive reset failures spawn a recovery agent (25 min cap) instead of stranding the loop on a roll at the frame edge.

What the reviewer will most likely find, in order

  1. Raise arm speed from 30 to 60–75 °/s. Halves motion time; also halves the harness reset, so more iterations per hour.
  2. Shrink the executor to one tool call and the done marker. Then a cheaper model with a small thinking budget suffices for the nominal path. The reviewer can rehearse the exact command from a few cells before the executor ever sees it.
  3. Trim waypoints in the technique (the via and hover legs) once the faster speed proves stable in the grasp photos.
  4. Fix whatever the far and near cells actually fail on, since the serpentine will keep handing them over.

Item 2 is the honest end state: the fastest executor is barely an agent. The agent's value is in recovery, and the reviewer's value is in getting it there.

What to watch on the first real iterations

  • Baseline block (iterations 1–3) at 30 °/s on cells c000, c001, c002. c000 is a hard far cell (r 0.38); expect a reset failure or a slow run there. If the executor cannot finish inside 180 s at baseline on a mid cell, the deadline is doing its job and the reviewer's first move is speed.
  • Kill behaviour. After the first killed run, check iters/iNNNN/home.jsonl shows homed: true and the next reset found the roll. That path is untested on hardware.
  • Cost. Each iteration records the executor's cost from the CLI result event; the reviewer's cost is in iters/reviews/rNNNN.stream.jsonl. Nothing logged cost before, so the first block sets the number.
  • Backup timer. It commits and pushes the repo hourly, including anything the reviewer left uncommitted. Harmless, but it means the reviewer's commit history is interleaved with data commits.

Handover to collection

When the last 9 runs are at or above 80 % and the median time to done has stopped falling: touch state/HALT_SPEEDLOOP, tag the tools, remove the factory's state/HALT, and start factory again. The factory's executor already calls the same episode.py and reads the same calib/motion.json, so the recorded episodes come out at the tuned speed. Curate those as their own speed regime; mixing 30 °/s and 70 °/s demonstrations in one training set teaches an ambiguous speed.
